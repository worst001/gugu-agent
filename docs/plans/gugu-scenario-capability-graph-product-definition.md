# Gugu 场景能力图谱产品定义

更新时间：2026-06-25

## 1. 背景

用户反馈的核心不是“想管理一个知识图谱”，而是：

> 希望 Gugu 能像一个懂业务场景的 Agent，自动判断当前任务适合什么模型、什么工具、什么行业表达方式，以及怎样把结果做得更像可交付内容。

典型表达是：有些产品的知识库能力好，但输出内容不够好；如果我们要推广 Gugu，需要让用户感受到它能适配行业、岗位和任务，而不是只回答泛泛内容。

因此，本需求不应被定义为一个用户可见的“知识图谱管理后台”，而应定义为一个隐藏在 Agent 内部的“场景能力路由系统”。

## 2. 产品定位

对外不叫“知识图谱”。用户不需要理解图谱、节点、边、RAG、GraphRAG 或向量库。

对内可以叫：

- 场景能力图谱
- 智能场景识别
- 任务能力路由
- Context Router

用户感知应该是：

- Gugu 更懂我现在要做什么。
- Gugu 会自动选合适的模型、工具、技能和工作流。
- Gugu 输出更像具体行业、具体岗位、具体平台可以直接用的交付物。
- Gugu 在必要时会告诉我“为什么这样做”，但不会让我配置复杂系统。

## 3. 当前版本决策

### 3.1 不发布“资料 / Profile”设置入口

之前实现的“资料 / Project Profile”更像一个手动填写项目画像的设置页。它有价值，但不是当前用户要的主路径：

- 小白用户不知道为什么要填。
- 容易被误解为需要先建知识库才能用。
- 容易让产品从“自动 Agent”变成“手动配置工具”。
- 当前阶段还没有足够完整的场景验证。

因此，当前版本默认隐藏这个设置入口。底层代码可保留为后续实验能力，但不作为用户可见功能发布。

### 3.2 保留内部任务路由能力

已经实现或规划中的任务识别、模型建议、工具箱路由、Skill 路由等能力仍然保留。这些能力符合“场景能力图谱”的方向。

需要保证：

- 内部 scaffold 只进入 wire，不显示给用户。
- 不污染用户消息气泡。
- 不污染会话标题。
- 不跨会话串上下文。
- 不默认启用跨会话记忆。
- 用户显式选择优先于自动判断。

## 4. 目标用户价值

### 4.1 对普通用户

用户只需要说：

- “帮我写一篇小红书品牌内容”
- “帮我做一份产品介绍 PPT”
- “分析这个表格”
- “帮我改这段代码”
- “帮我整理成日报”

Gugu 自动识别：

- 任务类型
- 行业或业务场景
- 目标平台
- 输入材料类型
- 目标交付物
- 应该使用的模型、技能、工具和检查清单

### 4.2 对推广和商业化

场景能力图谱不是卖“图谱功能”，而是支撑这些卖点：

- 面向不同岗位：运营、文案、选品、销售、财务、开发。
- 面向不同行业：电商、教育、本地生活、AI 产品、内容团队。
- 面向不同交付物：文案、PPT、表格、邮件、日报、代码。
- 让用户自己选择任务，但 Gugu 在背后自动补齐专业工作流。

## 5. V1 范围

V1 做“轻量、隐式、可解释”的场景能力路由。

### 5.1 做什么

- 根据用户输入、附件、工具箱选择和项目目录识别任务类型。
- 为任务选择少量相关上下文，不注入大段知识。
- 给模型路由提供建议，但不强制覆盖用户选择。
- 根据任务推荐 Skills、MCP、工具和检查清单。
- 在活动面板里用自然语言展示简短过程，例如：
  - 正在识别任务类型
  - 已识别：品牌内容 / 小红书文案
  - 准备使用：品牌内容检查清单
  - CodeGraph 不可用，改用普通代码检索
- 保证用户气泡、标题和历史记录干净。

### 5.2 不做什么

- 不做左侧栏“知识图谱”入口。
- 不做可视化图谱。
- 不让用户手动编辑节点和关系。
- 不默认开启 claude-mem。
- 不默认做跨 session 记忆。
- 不上传用户资料到云端形成知识库。
- 不引入图数据库或向量数据库。
- 不把聊天记录、附件、项目文件全量写入图谱。
- 不自动覆盖用户文件。
- 不自动发邮件、提交外部表单或执行高风险动作。

## 6. 核心场景

### 6.1 品牌内容

用户说：“帮我写一篇适合小红书的品牌内容。”

Gugu 应识别：

- 任务：品牌内容
- 平台：小红书
- 推荐模型：强模型
- 推荐检查清单：开头钩子、用户痛点、可信理由、转化动作、平台风格
- 是否需要 WebFetch：只有用户要求参考实时信息或竞品时才使用

输出目标：更像可发布的文案，而不是泛泛建议。

### 6.2 PPT

用户说：“帮我做一份产品介绍 PPT。”

Gugu 应识别：

- 任务：PPT 制作
- 推荐 Skill：`ppt-master`
- 输出策略：先大纲，再页结构，再生成文件
- 检查清单：页数、视觉风格、文字不溢出、结构完整

### 6.3 表格分析

用户上传 Excel 并说：“分析一下这个表格。”

Gugu 应识别：

- 任务：表格分析
- 推荐 Skill：`excel-master` / `spreadsheet-master`
- 检查清单：字段、行列规模、缺失、重复、异常、结论

### 6.4 编码

用户说：“看下这个报错，帮我修复。”

Gugu 应识别：

- 任务：编码 / Bug 修复
- 推荐能力：CodeGraph、Read、搜索、测试
- 检查清单：先定位、再修改、再验证，不误改无关文件

CodeGraph 是增强路径，不是强依赖。不可用时应退回普通代码检索。

## 7. 体验原则

- 用户先成功完成任务，再感知系统聪明。
- 不暴露内部术语。
- 不让用户先配置资料再使用。
- 不让隐藏 prompt 出现在聊天历史、标题或复制内容里。
- 自动判断必须可回退。
- 用户显式选择永远优先。
- 长任务必须让用户看到当前阶段和下一步。
- 所有失败都要给中文可操作建议。

## 8. 后续阶段建议

### P0：收口当前实现

- 默认隐藏“资料 / Profile”入口。
- 保留底层路由代码。
- 增加测试，防止内部 scaffold 泄漏到用户气泡和标题。
- 文档明确当前不发布“知识图谱 UI”。

### P1：场景识别稳定化

- 完善任务类型识别。
- 让工具箱、附件、项目目录共同参与判断。
- 修正模型路由：不要因为简单任务过度使用弱模型，高风险任务走强模型。

### P2：活动面板解释

- 把内部路由结果翻译成用户能理解的进度。
- 展示“正在识别 / 已识别 / 使用能力 / 回退原因”。
- 不展示内部 prompt 和实现细节。

### P3：场景模板

- 增加内置场景模板，例如运营日报、选品分析、品牌文案、产品 PPT、代码修复。
- 模板不作为用户必须填写的表单，而是 Agent 自动参考的工作流。

### P4：场景配置与样例库

后续不开放“项目资料 / Profile”作为设置栏。Codex 没有让用户手动维护项目资料，Gugu 也应保持这个方向：让用户直接提需求，由 Agent 自动识别任务场景。

P4 的重点改为维护内置场景配置和样例库：

- 品牌内容、PPT、表格分析、日报、邮件、代码修复等场景的检查清单。
- 不同行业、岗位、平台的轻量示例。
- 可解释的能力选择规则。
- 不要求用户填写资料。
- 不新增左侧栏或设置页入口。

### P5：长期知识能力

如果未来要做真正知识库或知识图谱，需要单独立项：

- 数据边界
- 存储成本
- 隐私策略
- 用户授权
- 索引生命周期
- 删除和导出能力
- 企业版权限模型

这不是当前 V1 要解决的问题。

## 9. 发布判断

当前版本可以发布的条件：

- 用户看不到“资料 / Profile”入口。
- 用户消息、标题和历史记录不出现内部 scaffold。
- 工具箱和任务路由能提升结果，但不会影响普通对话。
- 失败时不暴露内部错误。
- 不开放 `Project Profile` 设置入口；相关代码若继续保留，只能作为内部实验，不进入发布宣传。

当前版本不应宣传：

- 已支持知识图谱。
- 已支持企业知识库。
- 已支持跨会话长期记忆。
- 已支持用户资料自动沉淀。

当前版本可以宣传：

- Gugu 会根据任务自动选择合适能力。
- Gugu 更适合办公、内容、表格、PPT 和编码等具体场景。
- Gugu 在本地桌面环境中完成更多真实工作流。
